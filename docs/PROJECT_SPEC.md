## 1. 프로젝트 개요

### 1-1. 서비스명

MartPick(마트픽)

### 1-2. 해결하려는 문제

생필품을 여러 개 구매할 때는 개별 상품의 최저가보다 **한 판매점에서 장바구니 전체를 구매할 때의 총액**이 중요합니다.
한국소비자원 참가격 서비스에서도 가격 비교 기능을 제공하지만, 개발자가 확인한 장바구니 비교 화면에서는 사용자가 비교할 판매점을 직접 선택해야 했습니다.
(기존 서비스에 유사한 기능이 전혀 없다고 단정하지 않습니다.)

### 1-3. 제공 가치

- 사용자가 판매점을 직접 고르지 않아도, 선택 지역의 판매점을 자동으로 찾아 장바구니 총액을 비교합니다.
- 장바구니 상품의 가격이 모두 확인된 판매점만 완전 비교 목록(총액순 정렬)에 포함해, 누락 가격 때문에 총액이 왜곡되지 않도록 합니다.
- 모든 가격에 조사일을 함께 표시해 데이터의 기준 시점을 분명히 합니다.

### 1-4. 서비스 데이터 범위

- 데이터 출처: 한국소비자원 생필품 가격 정보 공공데이터 API
- 기준 조사일: **2026-09-25** (고정, R1)
- 상품: 상품 API가 제공하는 **전체 상품**(2026-09-29 조회 시 604개)을 수집하고 검색할 수 있습니다(4-2). 기준 조사일에 가격 데이터가 없는 상품도 포함합니다.
  - 초기 7개 상품은 가격 비교 로직 검증에 사용한 **기준 상품**이며, 수집 검증에도 계속 사용합니다(4-1-1).
- 지역: 시·도 단위 (R12)
- 제한된 데이터 범위는 화면과 README에 명시합니다.

### 1-5. 용어

| 용어 | 뜻 |
|---|---|
| 기준 조사일 | 비교에 사용하는 가격의 조사일. 모든 판매점에 같은 날짜를 적용합니다. |
| 완전 비교 목록 (총액순 정렬) | 장바구니의 모든 상품 가격이 기준 조사일에 확인된 판매점 목록. 장바구니 전체 총가격(`totalPrice`)을 계산해 R6 순서로 정렬합니다. |
| 부분 비교 목록 | 장바구니 상품 중 일부 상품의 가격만 확인된 판매점 목록. 전체 총가격은 계산하지 않고, 확인된 상품의 합계(`knownSubtotal`)만 제공합니다. |
| `totalPrice` | 완전 비교 판매점의 장바구니 전체 총가격 (모든 상품 소계의 합) |
| `knownSubtotal` | 부분 비교 판매점에서 가격이 확인된 상품 소계의 합. **장바구니 전체 총가격이 아닙니다.** |
| 가격 누락 | 기준 조사일에 해당 (판매점, 상품)의 가격 데이터가 없는 상태. |
| 비교 제외 판매점 | 본사 등 개별 방문 가능 매장으로 확인되지 않아 매장별 가격 비교 대상에서 제외하는 판매점 (R8). |

## 2. 화면 구성과 사용자 흐름

### 2-0. 화면 흐름

핵심 화면은 **상품 탐색 → 장바구니 → 가격 비교 결과**의 3개입니다. 회원가입·로그인 화면은 별도로 제공하며, 비회원과 회원 모두 같은 핵심 화면 흐름을 이용합니다.

```
[상품 탐색] --담기--> (상품 탐색 화면 유지, 담기 결과 안내)
     |
     +--장바구니 보기--> [장바구니] --지역 선택 + 비교 요청--> [가격 비교 결과]
     ^                                                            |
     +------------------------------------------------------------+
[회원가입] --가입 성공--> [로그인] --로그인 성공--> 로그인 전 화면(없으면 상품 탐색)
로그아웃 --> [상품 탐색]
```

**비회원 시나리오**

1. 상품 탐색 화면에서 상품을 찾아 담고, `장바구니 보기`로 장바구니 화면에 이동합니다.
2. 장바구니 화면에서 수량을 조정하고 비교할 시·도를 선택합니다.
3. 비교를 요청해 선택 지역의 판매점별 총액을 확인합니다.

**회원 시나리오** (Phase 5, 구현됨)

1. 회원가입 후 아이디·비밀번호로 로그인합니다.
2. 비회원과 같은 흐름으로 상품을 담고 비교합니다. 장바구니는 계정에 저장됩니다.
3. 로그아웃 후 다시 로그인해도 기존 장바구니를 불러옵니다.

### 2-1. 상품 탐색 화면

- 비회원도 사용할 수 있습니다.
- 검색 대상은 수집한 **전체 상품**입니다. 기준 조사일에 가격 데이터가 없는 상품도 검색되고 담을 수 있습니다.
- 검색어가 없으면 전체 상품을, 검색어가 있으면 **상품명 부분 일치**(앞뒤 공백 제거, 영문 대소문자 무시) 결과를 표시합니다.
- **서버 사이드 페이지네이션**: 한 페이지에 **30개**씩 표시합니다. 검색어가 있을 때도 결과를 페이지 단위로 표시합니다.
  - 정렬: 상품 ID 오름차순
  - 페이지 번호는 사용자에게 1부터 표시합니다.
  - 음수·0·숫자가 아닌 페이지 번호는 첫 페이지로, 전체 페이지 수를 넘는 번호는 마지막 페이지로 보정합니다.
  - 검색 결과가 0건이어도 정상 화면으로 처리합니다("검색 결과 없음" 안내).
- **검색어 제어 문자 검증**: 앞뒤 공백(탭·개행 포함)을 제거한 검색어에 제어 문자(NUL을 포함한 ISO 제어 문자: U+0000~U+001F, U+007F~U+009F)가 있으면 DB를 조회하지 않고 **HTTP 400**으로 응답합니다.
  - 화면에는 "검색어에 사용할 수 없는 문자가 포함되어 있습니다."를 표시하고, 그 검색어는 입력칸에 다시 쓰지 않고 검색어 없이 전체 상품 화면(요청한 페이지 번호 유지)을 보여 줍니다.
  - 이유: PostgreSQL은 문자열에 NUL(0x00)을 저장·비교할 수 없어, 그대로 조회하면 DB 예외로 500이 되었습니다. 다른 제어 문자는 DB에서 오류가 나지 않았지만 검색어로 의미가 없어 같은 방식으로 거부합니다.
  - 앞뒤의 공백·탭·개행은 제거되므로 거부 대상이 아닙니다(Java에서 공백으로 취급되는 U+001C~U+001F도 제거). 검색어 가운데의 탭·개행은 거부합니다. 정상적인 한글·영문·기호·이모지 검색어와 빈 검색어는 영향이 없습니다.
- 상품별 가격 데이터 유무는 표시하지 않습니다(Q30).
  - 대신 가격 데이터가 없는 상품은 비교 결과에서 가격 정보가 없을 수 있다는 **일반 안내 문구**를 화면에 표시합니다.
- 각 상품에 상품명과 규격을 표시합니다.
  - 상품명·규격은 상품 API 원문을 사용합니다(상품명 `goodName`, 규격 `goodTotalCnt` + `goodTotalDivCode`).
  - 상품명은 원문 그대로 표시하고, 규격 값이 있으면 `702 G`처럼 수치와 단위 코드 원문을 따로 표시합니다. 상품명 괄호 안 정보(예: `(18개입)`)와 규격 필드의 의미가 다를 수 있으므로 중복 여부를 판별하지 않으며, 일부 상품에서 같은 정보가 두 번 보이는 것은 허용합니다.
- **가격은 표시하지 않습니다.** 가격은 판매점마다 다르기 때문입니다.
- 별도의 수량 입력을 제공하지 않습니다.
  - `담기` 버튼을 누를 때마다 해당 상품 **1개**를 장바구니에 추가합니다.
  - 이미 담긴 상품이면 기존 수량에 1을 더합니다.
  - 더한 결과가 99를 넘는 추가는 거부하고 수량 제한을 안내합니다.
  - 수량 직접 변경은 장바구니 화면에서 처리합니다.
- `담기` 후에는 **상품 탐색 화면에서 이동하지 않고**, 담기 성공 여부를 사용자에게 안내합니다. 이때 **검색어와 페이지 번호를 유지**합니다.
  - 담은 상품의 카드 위치(`#product-{상품 ID}`)로 돌아가고, 담기 성공·실패 안내는 화면 상단이 아니라 **그 카드 안에** 표시합니다.
- 별도의 **`장바구니 보기`** 버튼으로 장바구니 화면에 이동합니다.
- 검색 결과가 없으면 "검색 결과 없음"을 안내합니다.

### 2-2. 장바구니 화면

**표시와 조작**

- 담긴 상품의 상품명, 규격, 수량을 표시합니다.
- 수량 변경과 삭제를 할 수 있습니다.
- 상품별 수량은 **1~99의 정수**만 허용합니다. 화면과 서버 양쪽에서 검증합니다.
- 비교 전 장바구니 화면에는 **상품별 가격이나 총액을 표시하지 않습니다.** 가격은 판매점마다 다르기 때문입니다.

**지역 선택과 비교 요청**

- 장바구니 화면에서 비교할 **시·도**를 선택하고 비교를 요청합니다.
- 지역 목록은 R12 기준으로 구성합니다. 비교 결과 화면에서도 같은 목록으로 지역을 바꿔 다시 비교할 수 있습니다(2-3).
- 선택한 지역은 회원 계정이나 장바구니에 **영구 저장하지 않습니다.** 가격 비교 요청의 조건으로만 사용합니다.
- 지역을 선택하지 않으면 비교를 진행하지 않고 **"비교할 지역을 선택해 주세요."**라고 안내합니다.
- 장바구니가 비어 있으면 비교를 진행하지 않고 "장바구니가 비어 있음"을 안내합니다.

**저장 방식 (비회원·회원)**

| 구분 | 저장소 | 유지 |
|---|---|---|
| 비회원 | 서버 세션(HttpSession)에 상품 ID와 수량 | 세션 만료 또는 로그아웃으로 세션이 무효화되면 사라짐 |
| 회원 (Phase 5, 구현됨) | DB | 재로그인 후에도 유지 |

- 비회원 세션 장바구니와 회원 DB 장바구니가 모두 구현되어 있습니다. 회원 장바구니의 DB 저장과 서비스 로직은 5-3, 장바구니·가격 비교 화면 연결은 5-4에서 구현했습니다.

- 별도의 회원 장바구니 URL이나 마이페이지를 두지 않습니다. 장바구니 URL은 비회원·회원이 같고, 서버가 로그인 여부에 따라 저장소를 선택합니다.
  - 비회원은 자신의 세션 장바구니만 사용합니다.
  - 로그인한 회원은 자신의 DB 장바구니만 사용합니다.
- 로그인 시 비회원 장바구니를 회원 장바구니에 **자동으로 병합하지 않습니다.** 로그인 전에 담은 비회원 장바구니는 회원 장바구니에 나타나지 않습니다.
  - 비회원이 장바구니 화면에서 상품이 담긴 장바구니를 보고 있으면 이 사실을 화면에서도 안내합니다(6-3 U1): "로그인하면 지금 담은 상품은 회원 장바구니로 옮겨지지 않습니다. 로그인한 뒤 다시 담아 주세요." 아래에 `로그인`·`회원가입` 링크(`continue=/cart`)를 둡니다. 장바구니가 비어 있거나 로그인한 회원이면 표시하지 않습니다. 저장·병합 정책은 바뀌지 않았습니다.
- 회원 장바구니는 본인만 조회·수정할 수 있습니다(R11).
  - **구현(5-3)**: `MemberCartService`의 모든 메서드는 회원 ID를 명시적으로 받고, Repository 조회·변경·삭제는 회원 ID와 상품 ID를 함께 조건으로 합니다(`findByMemberIdAndProductGoodId`, `deleteByMemberIdAndProductGoodId`, `findByMemberIdOrderByIdAsc`). 항목 ID나 상품 ID만으로 항목을 찾는 메서드는 만들지 않았습니다.
  - 수량 규칙(1~99, 99 초과 추가 거부, 거부 시 조정하지 않음)과 메시지는 비회원 장바구니와 같습니다. 담기지 않은 상품의 수량 변경·삭제는 아무 일도 하지 않으며, 수집되지 않은 상품은 담을 수 없고, 존재하지 않는 회원의 담기·변경·삭제는 "회원을 찾을 수 없습니다."로 거부합니다(조회는 빈 목록).
  - 표시 순서는 담은 순서(항목 ID 오름차순)이며 비회원 장바구니와 같습니다: 다시 담거나 수량을 바꿔도 순서는 그대로이고, 삭제했다가 다시 담으면 맨 뒤로 갑니다.
  - 동시성: 같은 회원의 담기·수량 변경·삭제는 같은 트랜잭션 안에서 먼저 회원 행에 쓰기 잠금(`PESSIMISTIC_WRITE`, PostgreSQL `for no key update`)을 걸어 직렬화합니다. 조회는 잠금을 걸지 않습니다. 다른 회원의 작업은 서로 막지 않습니다. 중복 행은 DB 유니크 제약(`uk_cart_item_member_product`)이 마지막 방어선입니다.
  - 목록 조회는 상품을 함께 읽어(`@EntityGraph`) 항목 수와 관계없이 SQL 1회로 처리하며, 서비스가 화면용 DTO(`CartItemView`)와 비교 입력(`CartLine`)을 만들어 반환합니다.
  - **현재 구현의 한계(존재하지 않는 회원)**: 담기·수량 변경·삭제는 존재하지 않는 회원이면 "회원을 찾을 수 없습니다."로 거부하지만, 조회(`items`, `lines`)는 같은 경우에도 빈 목록을 돌려줍니다. 그래서 조회만으로는 "존재하지 않는 회원"과 "장바구니가 빈 회원"을 구분할 수 없습니다. 조회에 회원 존재 확인을 넣으려면 쿼리를 추가하거나(비어 있을 때만 확인하면 빈 장바구니 조회가 SQL 2회) 쿼리 구조를 바꿔야 하므로(회원 기준 left join 단일 쿼리) 현행을 유지하기로 했습니다. 회원 삭제와 삭제된 회원의 세션 처리는 이번 범위 밖입니다.
  - **화면 연결(5-4)**: `CartController`(조회·담기·수량 변경·삭제)와 `CompareController`는 `CartService`만 호출합니다. `CartService`는 로그인한 회원이면 `MemberCartService`, 아니면 세션 장바구니(`GuestCartService`·`GuestCart`)로 위임하는 분기만 하며 장바구니 규칙이나 트랜잭션을 두지 않습니다. 회원 요청은 세션 장바구니를 읽거나 쓰지 않고, 비회원 요청은 DB 장바구니에 접근하지 않습니다.
  - 로그인해도 로그인 전 비회원 장바구니는 회원 장바구니로 옮겨지지 않고, 로그인 중에는 장바구니 조회·변경·가격 비교에 쓰이지 않으며, 로그인 과정에서 별도로 삭제하지도 않습니다(세션에 남아 있다가 로그아웃의 세션 무효화로 사라짐). 로그아웃은 회원 DB 장바구니를 지우지 않으며, 로그아웃 뒤에는 새 비회원 장바구니(빈 상태)가 표시됩니다. 화면에 회원 장바구니임을 나타내는 별도 문구는 두지 않습니다(Q36).
  - URL에 사용자 ID를 포함하지 않고, 서버가 인증 정보의 회원 ID로만 장바구니를 조회·수정합니다. **[제안]**
- 접근 제한 테스트 대상
  - 비회원 요청이 회원의 DB 장바구니에 접근할 수 없는지
  - 회원 A가 회원 B의 장바구니에 접근할 수 없는지
  - 구현 현황(5-4): 두 항목 모두 `MemberCartFlowTest`가 실제 필터 체인과 PostgreSQL로 확인합니다. 요청에 임의의 `memberId`·`member`·`id` 파라미터를 넣어도 무시됩니다.

### 2-3. 가격 비교 결과 화면

- 비회원도 사용할 수 있습니다.
- 사용자가 판매점을 선택하지 않아도, 선택 지역의 판매점을 자동으로 비교합니다.
- **기준 조사일**을 화면에 명확히 표시하고, 조사 가격이 실시간 판매 가격·재고를 보장하지 않는다는 문구를 표시합니다(R9).
- 결과는 두 영역으로 구분합니다.

| 영역 | 대상 | 표시 항목 |
|---|---|---|
| **완전 비교 목록 (총액순 정렬)** | 장바구니의 모든 상품 가격이 확인된 판매점 | 판매점명, 주소, 상품별 단가·수량·소계, 전체 총가격(`totalPrice`), 조사일 |
| **부분 비교 목록** | 일부 상품 가격만 확인된 판매점 | 판매점명, 주소, 확인된 상품별 단가·수량·소계, 누락된 상품 목록, 확인된 상품의 합계(`knownSubtotal`). **전체 총가격(`totalPrice`)이나 임의의 예상 금액은 제공하지 않음** |

- 완전 비교 목록은 R6 순서(총액 오름차순 → 판매점 ID 숫자 오름차순)로 정렬합니다.
- 부분 비교 목록은 판매점 ID 오름차순으로 정렬하며, `knownSubtotal` 기준 가격순으로 정렬하지 않습니다. 판매점마다 누락된 상품이 다를 수 있기 때문입니다.
- `knownSubtotal`은 누락 상품이 빠진 금액이므로 완전 비교의 `totalPrice`와 직접 비교하지 않으며, 부분 비교 판매점이 더 저렴하다고 표시하지 않습니다.
- 부분 비교 금액은 "확인된 상품 합계 6,700원 (햇반 제외)"처럼 누락 상품을 함께 표시합니다.
- **판매점 카드 표시 방식**
  - 상품별 단가·수량·소계 표(상세 가격표)는 **기본으로 접혀 있고**, 사용자가 펼쳐서 확인합니다. HTML `<details>`를 사용하며 키보드로도 펼치고 닫을 수 있습니다.
  - 접힌 상태에서도 항상 보이는 정보
    - 완전 비교: 판매점명, 주소, 장바구니 합계(`totalPrice`)
    - 부분 비교: 판매점명, 주소, 확인된 상품 합계(`knownSubtotal`), **가격 정보가 없는 상품 목록**
  - 가격 정보가 없는 상품 목록은 접지 않고 **항상 표시**합니다.
  - 완전 비교의 장바구니 합계는 강조해 표시하고, 부분 비교의 확인된 상품 합계는 중립적인 배경과 더 작은 글자에 "일부 상품 제외" 표시를 붙여 **시각적으로 구분**합니다. 부분 비교 금액이 장바구니 전체 가격으로 보이지 않도록 하기 위함입니다.
- **1위·2위 등의 순위 숫자는 표시하지 않습니다.** 순위 숫자를 표시하지 않더라도 정렬 순서는 항상 일정해야 합니다.
- 판매점 주소는 **도로명 주소가 있으면 도로명 주소, 없으면 지번 주소**를 표시합니다.
- 비교 가능한 판매점이 없으면 사유를 안내합니다(5장).
- **지역 변경(6-3 U3)**: 결과 화면 상단에 지역 선택(`<select>`, 비교 가능한 지역 목록)과 `다시 비교` 버튼을 둡니다. 현재 비교한 지역이 선택되어 있고, 같은 `GET /compare?areaCode=` 요청을 같은 장바구니로 다시 보냅니다. 선택한 지역은 요청에만 쓰며 세션이나 DB에 저장하지 않습니다. 계산과 정렬 정책은 그대로입니다.
- **판매점 목록 접기(6-3 U4)**: 완전 비교와 부분 비교는 각각 **처음 10곳만 펼쳐 보여 주고**, 나머지는 "나머지 N곳 보기" `<details>`(기본 접힘, JavaScript 없음)에 담습니다. 순서는 서비스가 정한 그대로입니다(완전 비교는 총액 오름차순, 같으면 판매점 ID 순서이고 부분 비교는 판매점 ID 순서). 가격순 정렬이나 순위 번호를 더하지 않으며 판매점을 빼거나 제외하지 않습니다. 영역이 10곳 이하이면 접기 표시가 없고, 11곳 이상이면 영역 설명에 "처음 10곳"을 안내합니다. 건수 표시(상단 이동 칩, 영역 제목)는 접힌 곳을 포함한 전체 판매점 수입니다. 처음 보이는 곳의 수는 `CompareController.PREVIEW_COUNT`(10)입니다.
  - 이유(2026-10-10 측정): 서울 기준 7종 비교는 판매점 106곳, HTML 약 317KB였고, 서울 108곳일 때 모바일 페이지 높이가 약 22,000px였습니다. 접으면 기준 7종(106곳)에서 약 4,700px입니다. 서로 완전히 같은 조건의 비교는 아닙니다.

### 2-4. 회원가입·로그인 화면

> Phase 5 구현 대상입니다. **회원가입(5-1)과 로그인·로그아웃(5-2)이 구현**되었습니다. 보안 설정은 비회원 화면 경로와 `/login`·`/signup`만 허용하고 CSRF 보호와 세션 고정 방어(Spring Security 기본값)를 유지합니다(6장).

**회원가입**

- 아이디와 비밀번호로 회원가입합니다.
  - 아이디: **영문·숫자 4~20자**, 중복 불가. **대소문자를 구분**합니다(`Abc123`과 `abc123`은 서로 다른 아이디, Q36). 화면 안내는 "영문·숫자 4~20자"로 간결하게 표시하며 대소문자 구분 정책은 안내 문구에 적지 않아도 유지됩니다.
  - 비밀번호: **최소 8자, 최대 72바이트**(UTF-8 기준, 한글은 한 글자가 3바이트). 대문자·특수문자 포함은 강제하지 않습니다. 앞뒤 공백을 자르지 않습니다. 화면 안내는 "8자 이상 입력해 주세요."만 표시하고 바이트 제한은 화면에 설명하지 않습니다. 72바이트를 넘으면 "비밀번호가 너무 깁니다. 입력 내용을 줄여 주세요."를 표시합니다(검증 규칙은 서버에서 그대로 적용).
  - **비밀번호 확인**: 비밀번호와 같은 값을 한 번 더 입력해야 하며, 서버에서 일치 여부를 검증합니다(Q36, 기존 스펙에 없던 사용성 개선). 확인 값은 저장하지 않습니다.
  - 검증에 실패하면 아이디만 다시 표시하고, **비밀번호와 확인 값은 화면에 다시 표시하지 않습니다.**
  - 필수 입력값을 서버에서 검증합니다.
  - 비밀번호는 BCrypt로 해싱해 저장합니다(평문 저장 금지).
  - 중복 가입은 사전 확인과 DB 유니크 제약(`uk_member_username`)으로 막습니다. 동시 요청으로 제약에 걸린 경우에도 **이 제약 위반일 때만** "이미 사용 중인 아이디"로 안내하고, 다른 DB 오류는 중복으로 오인해 안내하지 않습니다. (가입 화면의 중복 안내는 아이디 존재 여부를 알려 줍니다. 구분 금지는 로그인 실패 메시지에만 적용됩니다.)
- 가입 성공 후 **자동으로 로그인하지 않고** 로그인 화면으로 이동합니다. 가입 화면 하단에는 "이미 회원이신가요? 로그인" 링크(`/login`)가 있으며, 로그인 화면 하단의 회원가입 링크와 같은 스타일입니다.
- **가입 경로의 `continue` 유지(6-3 U2)**: 장바구니 등에서 회원가입으로 이동한 뒤에도 로그인 후 원래 화면으로 돌아올 수 있도록 `continue`를 가입 화면과 가입 후 로그인 화면까지 넘깁니다.
  - 머리글의 `회원가입` 링크는 `로그인` 링크와 같은 조건(`/products`, `/cart`, `/compare`)에서 현재 화면을 `continue`로 붙입니다. 로그인 화면의 `회원가입` 링크와 가입 화면의 `로그인` 링크도 허용된 `continue`를 유지합니다.
  - 가입 화면은 허용된 `continue`를 숨은 입력으로 유지하고, 가입에 성공하면 `/login?continue=…`로 이동하며(안내 메시지는 그대로), 입력 오류·중복 아이디로 가입 화면을 다시 보여 줄 때도 유지합니다.
  - **검증 정책은 새로 만들지 않고 기존 `ContinueUrl.resolve`와 허용 경로·쿼리 화이트리스트를 그대로 재사용**합니다. 가입 화면 표시, 가입 처리 후 이동 단계마다 다시 검증하며, 외부 URL·`//`·역슬래시·개행·허용되지 않은 경로·이미 인코딩되었거나 이중 인코딩된 값은 버리고(`continue` 없이 `/login`) 허용 경로의 허용되지 않은 쿼리는 걸러 냅니다.
  - 가입 화면에도 비회원 장바구니 안내를 둡니다: "비회원으로 담은 상품은 가입 후 로그인해도 장바구니에 자동으로 추가되지 않습니다." 로그인한 사용자의 POST `/signup`은 `continue`가 있어도 회원을 만들지 않고 `/products`로 이동합니다.
- 로그인·회원가입 화면은 제목·설명·카드를 같은 최대 너비(480px)로 가로 중앙 정렬합니다(2-5).
- URL은 `/signup`(회원가입), `/login`(로그인)입니다(Q36).

**로그인·로그아웃**

- Spring Security 세션 기반 인증을 사용합니다. JWT는 사용하지 않습니다.
- 로그인 후에는 **로그인 전에 접근하려던 서비스 내부 화면으로 복귀**합니다.
- 복귀 대상이 없거나 유효하지 않으면 **상품 탐색 화면**으로 이동합니다.
- **외부 URL은 로그인 후 이동 대상으로 허용하지 않습니다.**
- 로그인 시 비회원 장바구니와 회원 장바구니를 자동으로 병합하지 않습니다(2-2). 로그인 화면에 **짧은 고정 안내 문구**("비회원으로 담은 상품은 로그인 후 장바구니에 자동으로 추가되지 않습니다.")를 둡니다. 팝업이나 조건부 UI는 만들지 않습니다(Q36).
- 로그인 실패 시 "아이디 또는 비밀번호가 올바르지 않습니다." 한 가지 메시지만 표시합니다. 로그인 화면으로 돌아와도 입력한 아이디·비밀번호는 다시 표시하지 않습니다.
- 로그인 후 복귀는 `continue` 파라미터와 **허용 경로 화이트리스트**로 처리합니다(Q36). 허용 경로와 유지할 쿼리 이름은 2026-10-01 5-2 검토에서 **확정**했습니다.
  - 허용 경로는 GET 화면 `/products`, `/cart`, `/compare` 세 개뿐이며 정확히 일치해야 합니다. 외부 URL, 프로토콜 상대 URL(`//`), 역슬래시, 개행·제어문자, `#`, `;`, 경로 조작(`..`), POST 전용 경로(`/cart/items` 등), 인증 경로(`/login`·`/signup`·`/logout`)는 모두 차단하고 `/products`로 이동합니다.
  - 유지하는 화면 상태는 최소 범위입니다: `/products`는 `keyword`·`page`, `/compare`는 `areaCode`만 유지하고 `/cart`는 쿼리를 유지하지 않습니다. 그 외 쿼리 이름은 버립니다. 검색어는 길이 200자 이하여야 합니다.
  - 머리글의 `로그인` 링크는 복귀를 허용하는 화면(`/products`, `/cart`, `/compare`)에서만 현재 화면을 `continue`로 붙입니다. 로그인 실패로 다시 로그인 화면이 나와도 유효한 `continue`는 유지합니다.
  - 가격 비교 화면(`/compare`)으로 복귀하면 로그인한 회원의 장바구니로 비교합니다. 5-2 현재는 회원 장바구니가 아직 없어 세션 장바구니를 사용합니다.
- 이미 로그인한 사용자가 GET `/login`·`/signup`에 접근하면 `/products`로 이동합니다. 로그인 상태의 POST `/signup`은 회원을 만들지 않고 `/products`로 이동합니다. 로그인 상태의 POST `/login`은 인증 필터에 넘기지 않고 `/products`로 이동하므로 다른 계정으로 바뀌거나 세션이 교체되지 않습니다. Spring Security의 폼 로그인 필터는 기존 인증과 관계없이 다시 인증하므로(5-2에서 테스트로 확인) 별도 가드 필터(`AuthenticatedLoginGuardFilter`)로 막습니다. 가드는 로그인 필터와 같은 기준(컨테이너가 디코딩한 경로)으로 요청을 판단하므로 `/%6cogin` 같은 인코딩된 경로의 로그인 요청도 차단합니다(실제 Tomcat 테스트로 확인). CSRF 검사는 이 가드보다 먼저 수행됩니다.
- 로그아웃은 `POST /logout`(CSRF 필요)만 허용하고, GET 로그아웃은 거부합니다(처리하는 컨트롤러가 없는 경로이므로 404). 로그아웃하면 세션을 무효화하고 `/products`로 이동합니다. 머리글에는 로그인 상태이면 `아이디님`과 `로그아웃` 버튼, 아니면 `로그인`·`회원가입` 링크를 표시합니다.
- 로그인해야만 볼 수 있는 화면이 없으므로, 허용 목록 밖의 경로는 로그인 화면으로 보내지 않고 **거부**합니다(`anyRequest().denyAll()` 유지). 저장된 요청(Request Cache)은 쓰지 않으며(`NullRequestCache`), 거부된 요청이 세션을 만들지도 않습니다.
  - 거부한 요청의 상태 코드는 `DeniedRequestHandler`가 정합니다(비회원의 거부는 진입점, 로그인한 사용자의 거부와 CSRF 실패는 접근 거부 핸들러). 접근을 허용할지는 Spring Security가 그대로 판단하며, 이 핸들러는 어떤 요청도 새로 허용하지 않습니다.
    - 이 경로를 처리하는 컨트롤러가 없으면 **404**(없는 주소)입니다. 비회원과 로그인한 사용자가 같습니다. 예: `/admin`, `/actuator/*`, `/products/`, `GET /logout`.
    - 컨트롤러는 있는데 허용 목록에 없어 거부했다면 **403**입니다. 현재는 모든 컨트롤러 경로가 허용 목록에 있어 해당하는 경로가 없으며, 앞으로 허용 목록에서 빠진 경로가 생기면 403으로 드러납니다.
    - **CSRF 검증 실패는 경로와 관계없이 항상 403**입니다.
    - 컨트롤러 매핑을 확인할 수 없는 모든 경우(매핑 조회 실패, 경로 조건 없음 등)는 403으로 거부합니다.
  - 한계: 404와 403이 다르게 보이므로 "컨트롤러가 있는데 허용되지 않은 경로"와 "없는 경로"를 구분할 수 있습니다. 이 구분은 응답 상태에만 영향을 주며, 허용 목록 밖 경로는 내용을 돌려주지 않습니다(테스트 전용 컨트롤러로 확인).
- 로그인 실패 시 오류 메시지를 표시하되, **아이디 존재 여부를 구분해 노출하지 않습니다.**
- 로그아웃 시 인증 세션을 종료하고 **상품 탐색 화면**으로 이동합니다.
- Spring Security 기본 CSRF 보호를 유지합니다.

### 2-5. 화면 공통 정책 (그린 UI, Q35)

화면 표현에 관한 정책입니다. 2-1~2-3의 기능과 3장의 비즈니스 규칙은 바꾸지 않습니다.

**디자인**

- 흰색·연한 그린·짙은 그린 중심으로 구성하고, 주요 버튼과 금액은 대비가 충분하도록 표시합니다.
- 화면의 서비스 표기는 한글 **"마트픽"**이며, 로고는 장보기 심볼과 "마트픽" 텍스트를 함께 씁니다. 로고와 아이콘은 템플릿 안의 SVG로 그리고 외부 이미지 파일이나 웹 폰트는 사용하지 않습니다(시스템 글꼴).
- **표시하지 않는 것**
  - 상품 사진: 수집 데이터에 상품 이미지가 없으므로 임의의 사진이나 외부 이미지 URL을 쓰지 않습니다.
  - 판매점 브랜드 로고, 순위 숫자(R6·Q13), "최저가" 배지
  - 머리글의 장바구니 담은 개수

**화면별 보조 기능**

- 공통: 머리글에서 현재 메뉴를 강조하고 `aria-current`로 알립니다.
- 상품 탐색: 검색어가 있을 때 "검색어 지우고 전체 보기" 링크를 표시합니다. 페이지 이동에 첫 페이지·마지막 페이지 링크를 둡니다.
- 로그인·회원가입: 제목·설명·폼 카드를 같은 최대 너비(480px)로 가로 중앙 정렬하고, 좁은 화면(768px 이하)에서는 머리글의 로그인 영역을 다음 줄로 내립니다.
- 장바구니: "상품 N종 · 총 M개" 요약을 표시합니다. 가격이 아니라 상품 종류 수와 수량 합계입니다(2-2의 가격 미표시 정책 유지).
- 가격 비교 결과
  - 완전 비교·부분 비교 영역 바로가기 링크를 둡니다.
  - 정렬 설명 문구 (정렬 기준 자체는 R6과 2-3 그대로입니다)
    - 완전 비교: "장바구니 합계가 낮은 순서로 보여 줍니다. 합계가 같으면 판매점 번호순으로 표시됩니다." 실제 정렬은 총액 오름차순, 같으면 판매점 ID 숫자 오름차순입니다.
    - 부분 비교: 가격순으로 정렬하지 않는 이유와 함께 "판매점 번호순으로 표시됩니다."라고 안내합니다. 실제 정렬은 판매점 ID 숫자 오름차순입니다.
    - 화면의 "판매점 번호"는 판매점 ID를 뜻합니다.
  - 판매점별 상세 가격표에는 화면에 보이지 않는 표 제목(caption)을 붙여 화면 낭독기에서 어느 판매점의 표인지 알 수 있게 합니다.

**반응형**

- 가로 스크롤 없이 데스크톱·태블릿·모바일(375px 폭)에서 사용할 수 있게 합니다.
- 900px 이하에서는 장바구니 화면의 상품 목록과 지역 선택 패널을 한 열로 배치합니다.
- 480px 이하에서는 상품 카드를 2열로 표시하고, 판매점 카드의 금액 영역을 판매점명·주소 아래로 내립니다.


**오류 화면**

- 403, 404, 그 밖의 4xx, 5xx 오류는 Spring Boot 기본 화면(영어 Whitelabel) 대신 기존 화면 레이아웃(머리글·푸터·빈 상태 스타일)을 쓰는 한국어 화면으로 안내합니다. 템플릿은 `templates/error/{403,404,4xx,5xx}.html`이며 공통 본문은 `fragments/layout`의 `errorPanel`입니다. `@ControllerAdvice`는 쓰지 않습니다.
- HTTP 상태 코드와 화면 내용이 일치합니다: 404 "페이지를 찾을 수 없습니다", 403 "접근할 수 없습니다", 4xx "요청을 처리할 수 없습니다(오류 코드 표시)", 5xx "일시적인 오류가 발생했습니다(오류 코드 표시)". 모든 화면에 `상품 찾기로 이동`과 `장바구니 보기` 링크를 둡니다.
- 예외 이름, 예외 메시지, 스택 트레이스, DB 정보는 화면에 표시하지 않습니다. 화면이 아닌 요청(JSON)에는 Spring Boot 기본 JSON(`timestamp`, `status`, `error`, `path`)만 돌려줍니다.
- 확인 범위: 404·403·405는 실제 Tomcat의 오류 디스패치로, 5xx는 서버 오류 때 컨테이너가 넘기는 것과 같은 요청 속성으로 `/error`를 호출해 확인했습니다. 5xx를 실제 요청으로 일으키는 경로는 없어 재현하지 못했습니다. `/error`를 직접 열었을 때의 화면은 확인하지 않았습니다.

## 3. 비즈니스 규칙

### 3-1. 가격 비교 규칙

| # | 규칙 |
|---|---|
| R1 | **동일한 조사일의 가격만 비교합니다.** 모든 판매점에 같은 조사일을 적용합니다. 초기 버전의 기준 조사일은 **2026-09-25로 고정**하며, 사용자가 조사일을 선택하는 기능은 두지 않습니다. 이후 다른 날짜의 데이터를 수집하더라도 서로 다른 조사일의 가격을 섞어 비교하지 않습니다. |
| R2 | 동일한 상품 ID로 가격을 매칭합니다. |
| R3 | 판매점별 총액 = Σ(상품 가격 × 수량) |
| R4 | 장바구니의 **모든 상품 가격이 확인된 판매점만** 전체 총가격(`totalPrice`)을 계산해 완전 비교 목록(총액순 정렬)에 포함합니다. 일부 상품 가격만 있는 판매점은 부분 비교 목록에 확인된 상품별 가격·소계, 누락 상품 목록, 확인된 상품의 합계(`knownSubtotal`)를 제공하며, 전체 총가격이나 예상 금액은 제공하지 않습니다. `knownSubtotal`은 가격순 정렬이나 완전 비교 총가격과의 비교에 사용하지 않습니다. 장바구니 상품 가격이 하나도 확인되지 않은 판매점은 결과에서 제외합니다. |
| R5 | 가격이 없는 상품을 **0원으로 처리하지 않습니다.** 가격이 없다는 이유만으로 품절이라고 표현하지 않습니다. 가격 누락은 기준 조사일에 해당 (판매점, 상품)의 가격 데이터가 없는 것으로 판별합니다. |
| R6 | 완전 비교 목록은 **총액 오름차순**으로 정렬하고, 총액이 같으면 **판매점 ID 숫자 오름차순**으로 정렬합니다. 판매점 ID는 32비트 정수 범위를 넘는 값이 있으므로 `Long`으로 다룹니다. 화면에는 순위 숫자를 표시하지 않습니다. |
| R7 | 선택 지역 외 판매점은 비교에서 제외합니다. |
| R8 | 본사 등 **개별 방문 가능 매장으로 확인되지 않는 판매점**은 매장별 가격 비교 대상에서 제외합니다. 판별 기준은 판매점명 패턴 `(본사)`와 개발자가 직접 확인한 제외 ID 목록(`62`, `115`, `150`, `2160`)입니다. 규칙의 한계는 README에 명시합니다. |
| R9 | 조사일을 화면에 명시하고, 조사 가격이 **실시간 판매 가격·재고를 보장하지 않는다**는 문구를 표시합니다. |
| R10 | API의 `Y/N` 필드 등 의미를 확인하지 못한 필드는 임의로 해석하지 않으며 계산·표시에 사용하지 않습니다. |
| R11 | 사용자별 장바구니 접근 권한은 서버에서 검증합니다. |
| R12 | 지역 선택 목록은 **기준 조사일에 가격 데이터가 있는 판매점의 시·도 코드**로 구성합니다. 전체 상품을 수집하면 "수집한 상품 중 하나 이상의 가격이 기준 조사일에 있는 판매점"을 뜻합니다. |

### 3-2. 규칙별 보충 설명

**R6 동점**

- 실제 데이터에서 같은 시·도 안에 총액이 같은 판매점이 많아 보조 정렬이 자주 적용됩니다(API_RESEARCH 6-4).
- 판매점 ID를 문자열로 정렬하면 숫자 순서와 달라지므로 반드시 숫자 기준으로 정렬합니다(API_RESEARCH 3-1).

**R8 본사 제외**

- 판매점명에 `(본사)`가 붙은 판매점 4곳(62 CU, 115 세븐일레븐, 150 GS25, 2160 이마트24)에는 기준 조사일 가격 데이터가 있습니다. 이 가격이 전국 공통 가격인지, 권장 가격인지, 본사에서 직접 판매하는 가격인지는 확인되지 않았습니다. 따라서 "본사는 상품을 판매하지 않는다"고 단정하지 않으며, **개별 방문 가능 매장으로 확인되지 않아 매장별 가격 비교 대상에서 제외**합니다.
- 판매점 데이터에서 편의점 업태(`CS`)는 위 4곳뿐이고 개별 편의점 매장은 등록되어 있지 않습니다. 따라서 R8을 적용하면 **결과적으로** 편의점이 비교 결과에 나타나지 않습니다. R8은 편의점 업태 전체를 제외하는 규칙이 아니며, 이 사실을 README에 명시합니다.
- `본점`(예: 신세계백화점본점)이나 `(주)`가 들어간 판매점은 개별 매장이므로 제외 패턴에 포함하지 않습니다.
- 근거: API_RESEARCH 3-4, 6-6

**R12 지역 목록**

- 본사 등 비교 제외 판매점(R8)은 지역 목록 구성에서도 제외합니다.
- 공통 코드상 광주·전남은 "(구)" 코드(`020200000` (구)광주광역시, `021200000` (구)전라남도)와 새 코드(`021800000` 전남광주통합특별시)가 함께 있고, 새 코드 판매점 15곳 중 14곳은 옛 코드에 같은 이름·다른 판매점 ID로 등록된 판매점이 있습니다(동일 매장인지는 미검증). 조회한 9개 상품 기준으로는 기준 조사일 가격이 옛 코드 판매점에 없었습니다(API_RESEARCH 3-3, 6-5).
- 따라서 **(구)광주·(구)전남 코드는 목록에 표시되지 않습니다.** 전체 상품 수집(2026-10-01) 후에도 옛 코드 판매점의 기준 조사일 가격은 0건이었습니다(API_RESEARCH 10-3).
- 기존 지역 코드나 판매점 데이터를 영구 삭제하거나, 서로 다른 판매점 ID를 임의로 병합하지 않습니다.
- 향후 다른 조사일을 지원하게 되면 해당 날짜의 데이터로 다시 판단합니다.
- 부분 비교 판매점만 있는 시·도도 목록에 나타날 수 있으며, 이 경우 비교 결과에서 "완전 비교 가능한 판매점 없음"을 안내합니다.
- 지역 선택 목록과 비교 요청의 지역 검증은 같은 기준을 사용합니다. 목록에 없는 지역(예: (구) 코드)으로는 비교할 수 없습니다.
- **상품 범위 조건**: 지역 목록 조회에는 상품 ID 조건을 두지 않고, 수집한 모든 상품의 가격을 기준으로 합니다(기존 쿼리 유지).
  - 장바구니 상품의 가격이 선택 지역에 없으면 비교 결과에서 "가격이 확인된 판매점 없음"을 안내하므로(5장), 장바구니 구성에 따라 지역 목록을 바꾸지 않습니다.
  - 전체 상품 수집 후 확인 결과, 비교 가능 지역은 수집 전과 같은 16개였고 지역 목록 쿼리 실행 시간은 0.34ms였습니다(API_RESEARCH 10-3).

## 4. 데이터 수집 및 관리

### 4-1. 저장과 사용

- 사용자 요청마다 외부 API를 호출하지 않습니다. **수집한 데이터를 PostgreSQL에 저장한 뒤** 비교에 사용합니다.
- 가격은 조사일과 함께 저장합니다. **판매점·상품·조사일 조합**은 중복 저장하지 않습니다(DB 유니크 제약).
- 사용하는 API 오퍼레이션: 상품 정보 `getProductInfoSvc.do`, 판매점 정보 `getStoreInfoSvc.do`, 가격 정보 `getProductPriceInfoSvc`(`.do` 없음), 공통 코드 `getStandardInfoSvc.do`(지역 `classCode=AR`). 응답 형식과 필드는 API_RESEARCH 1~5장을 따릅니다.
- 확인된 호출 제한: 2,000회/일
- 수집 방식: **상품 API 응답에 있는 전체 상품**을 수집 대상으로 하고, 상품 ID별로 기준 조사일 가격을 조회합니다. 상품 ID를 설정에 나열하지 않습니다. 상품 ID 조회 1회로 해당 상품의 전국 판매점 가격을 받을 수 있습니다(API_RESEARCH 5장).
  - 1회 수집의 예상 호출: 지역 코드 1, 판매점 1, 상품 1, 가격은 상품 수만큼(604개 기준 약 604회)으로 **약 607회**입니다(예상값). 재시도는 별도입니다(4-1-1).
- 수집 실행 방법: 스케줄러 없이 개발자가 수동으로 **웹 서버 없이 1회** 실행합니다. 정기 자동 수집은 구현하지 않습니다(7장).
  - 명령: `./gradlew.bat bootRun --args="--martpick.collect.run=true --spring.main.web-application-type=none"`
  - 대상 DB는 `spring.datasource.url`·`username`(명령행 인자) 또는 `MARTPICK_DB_*` 환경변수로 지정합니다. 명령행 인자가 환경변수와 `application.yml`보다 우선합니다. 비밀번호는 명령행에 적지 않고 환경변수(`SPRING_DATASOURCE_PASSWORD` 또는 `MARTPICK_DB_PASSWORD`)로 넘깁니다.
  - 웹 서버 없는 모드에서는 웹 보안 설정(`SecurityConfig`)을 등록하지 않습니다. 이 모드의 컨텍스트 시작과 수집 실행기 동작은 테스트(`NonWebCollectRunTest`)로 확인했습니다. 실제 실행에서 수집 후 프로세스가 스스로 종료되는지는 아직 확인하지 않았습니다.
  - 2026-10-01 첫 전체 수집 당시에는 `SecurityConfig`가 웹 서버 없는 모드에서 앱 시작을 막는 문제가 있어, 로컬 전용 웹 모드(`--server.address=127.0.0.1 --server.port=0`)로 실행하고 수집 후 프로세스를 직접 종료했습니다. 이 문제는 이후 수정했습니다.

### 4-1-1. 수집 절차와 재수집 정책

- **조회 → 검증 → 저장**: 모든 API 응답을 받아 검증한 뒤, 단일 트랜잭션으로 저장합니다.
- **실패 시 DB 변경 없음**
  - API 호출이 하나라도 최종 실패하거나 필수 검증을 통과하지 못하면 중단하고 DB를 변경하지 않습니다. 기존 데이터는 그대로 유지됩니다.
  - 전체 응답을 검증한 뒤 단일 트랜잭션으로 저장하는 정책은 전체 상품 수집에서도 유지합니다.
- **제한적 재시도 (일시적 오류만)**
  - 재시도 대상: 네트워크 오류(연결 실패, 타임아웃), HTTP 5xx
  - 재시도하지 않음: 인증키 누락·잘못된 인증키(HTTP 401 등 4xx), `resultCode`가 `00`이 아닌 응답, 응답 형식·데이터 오류, 필수 검증 실패
  - HTTP 429는 이번 단계에서 재시도하지 않습니다.
  - 호출 1건당 최대 2회 재시도(총 3회 시도), 재시도 전 대기 1초·2초
  - 수집 1회의 추가 재시도는 모두 합쳐 최대 30회입니다. 넘으면 중단합니다(일일 호출 제한 2,000회 보호).
  - 재시도가 발생하면 호출 구분과 횟수를 수집 보고에 기록합니다(인증키 제외).
- **필수 검증 (하나라도 실패하면 저장 중단)**

| # | 검증 |
|---|---|
| V1 | 공통 코드 응답에서 `highCode=020000000`인 시·도 코드가 있고, 모든 판매점의 `entpAreaCode`가 그 시·도 코드에 속함 |
| V2 | 상품 응답의 상품 ID가 중복되지 않고, **기준 상품 7개가 상품 응답에 모두 있음** |
| V3 | 판매점 ID가 중복되지 않음 |
| V4 | **기준 상품 7개**는 각각 기준 조사일 가격이 1건 이상 있음 |
| V5 | 가격의 판매점 ID가 모두 판매점 응답에 있음 |
| V6 | 같은 판매점·상품·조사일의 가격이 중복되지 않음 |

  - 기준 상품 외의 상품은 기준 조사일 가격이 0건이어도 **정상**입니다. API의 정상 빈 응답(`resultCode=00`, 빈 `result`)은 오류가 아닙니다.
  - V4를 기준 상품에 유지하는 이유: 사전 조사에서 기준 조사일 가격이 확인된 상품이므로(API_RESEARCH 6-3), 이 상품들의 가격이 비면 부분 응답이나 API 이상을 의심할 수 있습니다.
- **가격 재수집**
  - 기준 조사일의 기존 가격을 **수집한 전체 상품 범위**에서 삭제한 뒤 새 응답으로 교체합니다.
  - 다른 조사일의 가격은 변경하지 않습니다.
- **검증의 구분**
  - **API 응답 검증**: 저장 전에 API 응답 자체가 믿을 만한지 봅니다. 대상은 호출 실패 판단(4-3), 필수 검증 V1~V6, 가격 급감 안전장치 G1·G2입니다. V7은 미확정입니다.
  - **저장 후 건수 검증**: 저장 직후 DB의 기준 조사일 전체 가격 건수와 가격 보유 상품 수가 **검증을 통과한 응답에서 계산한 값**과 같은지 확인합니다. 다르면 트랜잭션을 롤백합니다.
  - 저장 후 건수가 일치한다는 것은 **응답을 빠짐없이 저장했다는 뜻일 뿐**, API 응답이 완전하다는 근거가 아닙니다. 응답의 완전성은 API 응답 검증으로만 판단합니다.
- **가격 급감 안전장치** — 가격 존재 검증(V4)과 구분되는, 이전 가격 건수 대비 감소 검증입니다.
  - 초기 7개만 저장된 DB의 전체 건수와 전체 수집 결과를 직접 비교하지 않습니다.
  - **G1. 기준 상품 급감** (보조 장치, 기존 비교 기능의 회귀 검증용): 기준 상품 7개 각각의 새 가격 건수를 DB에 있는 **같은 상품**의 기준 조사일 가격 건수와 비교합니다. 기존 건수가 0이면 적용하지 않습니다. 첫 전체 수집부터 적용합니다.
  - **G2. 전체 건수 급감** (주요 안전장치): 같은 조사일의 **최신 FULL 성공 이력**(`collection_run`)에 기록된 전체 가격 건수와 가격 보유 상품 수를 기준으로 새 수집 결과를 비교합니다.
    - 이전 FULL 성공 이력이 없으면 G2를 적용하지 않고, 수집 보고에 "이전 전체 수집 이력 없음, G2 미적용"을 기록합니다.
    - 첫 전체 수집이 이 경우입니다. 첫 전체 수집 전에 기존 7개 상품 가격만 저장되어 있던 상태는 정상적인 초기 상태로 취급했으며, 7개 상품 수집은 FULL 이력으로 기록하지 않았습니다.
    - 2026-10-01 첫 전체 수집으로 FULL 성공 이력(ID 1)이 생겼으므로, 같은 조사일을 다시 수집하면 G2가 적용됩니다.
    - 설정 파일 수동 기록, 상품·가격 데이터 존재 여부로 이력 추론, 별도 실행 모드(초기 확장 모드)는 사용하지 않습니다.
  - 첫 전체 수집의 불완전 응답 감지: G2를 적용할 수 없으므로 V1~V6, V4, G1과 수집 보고(가격 0건 상품 수 등)에 의존합니다.
    - 상품별 조회와 판매점별 조회 결과를 대조하는 **V7(판매점 기준 교차 검증)**은 **미확정**입니다. 실제 API에서 두 조회의 결과가 일치하는지 확인한 뒤 채택 여부를 결정합니다.
  - 임계값: G1·G2 모두 새 건수가 기존의 **80% 미만**이면 중단합니다(임시 기준).
    - 80%는 **데이터 완전성을 증명하는 값이 아니라**, 급감을 탐지하기 위한 임시 안전장치 기준입니다.
    - 기준 조사일이 과거 날짜로 고정되어 있어, 같은 날짜를 다시 수집하면 거의 같은 데이터가 와야 합니다. 큰 감소는 부분 응답의 신호로 봅니다.
    - 같은 날짜를 재수집할 때 자연스럽게 생기는 변동 폭은 아직 관찰하지 않았습니다. 전체 수집을 두 번 이상 실행해 변동을 관찰한 뒤 다시 검토합니다.
  - 이 기준은 **데이터 완전성을 증명하는 기준이 아니라**, 부분 응답으로 기존 가격을 잘못 지우지 않기 위한 **임시 안전장치**입니다.
  - 의도한 감소라면 `martpick.collect.allow-shrink=true`로 저장을 허용할 수 있습니다. 이 경우에도 필수 검증 V1~V6은 생략하지 않습니다.
- **전체 수집 성공 이력 (`collection_run`)**
  - **성공한 전체 수집만** 기록합니다. 실패하면 트랜잭션이 롤백되므로 이력이 남지 않으며, 실패 원인은 로그와 수집 보고로 확인합니다.
  - 기록 항목: 기준 조사일, 상품 수(상품 응답 기준), 가격 보유 상품 수, 전체 가격 건수, 완료 시각
  - 수집 범위 컬럼은 두지 않습니다. 현재 이 테이블에는 전체 수집만 기록하므로 값이 항상 같기 때문입니다. 다른 범위의 수집을 기록해야 할 때 새 마이그레이션으로 추가합니다.
  - Flyway 새 마이그레이션으로 추가하며, 기존 V1 마이그레이션은 수정하지 않습니다.
  - **원자성**: 가격 교체, 저장 후 건수 검증, 이력 저장을 **같은 트랜잭션**에서 처리합니다. 어느 단계에서든 실패하면 가격 교체와 이력 저장이 함께 롤백됩니다.
  - **이력과 DB 불일치**: 최신 FULL 이력의 전체 가격 건수·가격 보유 상품 수가 DB의 실제 기준 조사일 값과 다르면, API 호출 전에 즉시 중단하고 두 값을 보고합니다. 트랜잭션 시작 시에도 한 번 더 확인합니다. 자동으로 보정하거나 무시하는 옵션은 두지 않으며, 원인을 확인한 뒤 다시 실행합니다. `allow-shrink`로도 우회할 수 없습니다.
  - **검사의 한계**: 이력·DB 정합성 확인과 저장 후 건수 검증은 **건수만 비교하는 수량적 정합성 검사**입니다. 개별 가격 값이 같은지, 어떤 (판매점, 상품) 행으로 구성되었는지까지는 보장하지 않습니다. 예를 들어 건수를 유지한 채 가격 값이 바뀌거나 행이 다른 행으로 바뀐 경우는 감지하지 못합니다.
- **운영 전제**: 같은 조사일의 수집은 동시에 실행하지 않습니다. 동시 실행을 막는 잠금은 구현하지 않습니다.
- **판매점·상품·지역 코드**
  - 판매점과 지역 코드(시·도 18개)는 응답 값으로 갱신하거나 추가합니다.
  - 응답에서 사라진 기존 판매점은 삭제하지 않고 수집 보고에만 기록합니다.
  - 상품은 상품 API 응답의 **전체 상품**을 응답 값으로 갱신하거나 추가합니다. 가격 데이터가 없는 상품도 저장합니다.
  - 응답에서 사라진 기존 상품은 삭제하지 않고 수집 보고에만 기록합니다. 장바구니·가격이 참조할 수 있기 때문입니다.
  - 본사 제외 여부는 수집할 때마다 판매점명 `(본사)` 패턴과 제외 ID 목록으로 다시 판정합니다(R8).
- **저장 방식**
  - 가격 저장은 기존 JPA 방식을 우선 유지합니다. 저장 시간과 메모리를 1만 건 → 5만 건 → 필요 시 25만 건 순서로 측정하고, 필요할 때만 일괄 삽입(`JdbcTemplate`)을 검토합니다.
  - 성능 측정은 개발 DB가 아닌 테스트 환경에서만 수행합니다.
  - 판단 기준: 저장에 5분을 넘기거나 메모리가 부족한 경우 (5분은 임시 기준)
- **수집 보고**
  - 상품별 건수를 모두 나열하지 않고 요약합니다: 전체 상품 수, 가격이 있는 상품 수, 가격이 없는 상품 수, 전체 가격 건수, 기준 상품별 가격 건수, 재시도 횟수, G2 적용 여부와 비교 기준 값
  - 향후 개선 후보 (미구현): 재수집할 때 전체 상품의 상품별 가격 건수 변화를 직전 수집과 비교해 **진단용으로만** 보고합니다(저장은 막지 않음). G2가 잡지 못하는 일부 상품의 누락을 사람이 확인하기 위한 것입니다. 가격 건수가 적은 상품이 많아(첫 전체 수집 기준 1~99건 상품 145개) 비율만으로는 오탐이 많으므로, 도입 시 절대 건수와 비율을 함께 쓰는 기준이 필요합니다.
- **정책 유지와 재검토 시점**: 현재 G1·G2·V4를 유지합니다. 기준 상품 7개를 계속 특별 취급할지는 실제 재수집 사례가 생기거나 기준 조사일을 바꿀 때 다시 검토합니다.
- **참고 신호 (저장은 진행하고 수집 보고에 기록)**
  - 판매점 응답 건수, 상품 응답 건수가 100의 배수로 딱 떨어지는 경우 (상품별 가격 건수에는 적용하지 않음)
  - `(본사)` 판매점이 제외 ID 목록과 일치하지 않는 경우
  - 응답에 없는 기존 판매점·상품
  - 조사 당시 건수(판매점 630곳, 상품 604개, 기준 상품 가격 2,926건 등)는 비교용 참고값이며 고정된 정답이 아닙니다.

### 4-3. API 호출 실패와 빈 결과

- 판단 기준
  - 정상: HTTP 200이고 `resultCode=00`. 결과가 없으면 빈 `result`로 옵니다.

  - HTTP 200이면서 실패인 응답이 실제로 확인되었으므로, **`resultCode`를 반드시 확인**합니다(API_RESEARCH 7장).

## 5. 예외 및 경계 상황

| 상황 | 처리 방침 |
|---|---|
| 빈 장바구니로 비교 요청 | 비교를 수행하지 않고 "장바구니가 비어 있음"을 안내합니다. |
| 지역을 선택하지 않고 비교 요청 | 비교를 진행하지 않고 "비교할 지역을 선택해 주세요."라고 안내합니다. |
| 잘못된 비교 요청: 장바구니에 비어 있는(null) 항목, 수집되지 않은 상품(0·음수 ID 포함), 같은 상품 중복, 비교 가능 지역 목록에 없는 지역 | 비교를 진행하지 않고 잘못된 요청으로 처리합니다. 검증 순서는 빈 장바구니 → 비어 있는 항목 → 지역 미선택 → 수량 범위 → 상품 중복 → 비교 불가 지역 → 미수집 상품입니다. |
| 검색 결과가 없는 상품 | "검색 결과 없음"을 안내합니다. |
| 검색어에 제어 문자(NUL 등)가 있음 | DB를 조회하지 않고 HTTP 400과 "검색어에 사용할 수 없는 문자가 포함되어 있습니다." 안내를 표시하고 전체 상품 화면을 보여 줍니다(2-1). |
| 없는 주소(처리하는 컨트롤러가 없는 경로) | HTTP 404와 "페이지를 찾을 수 없습니다" 화면. 허용 목록 밖 경로도 404이며 로그인 여부와 관계없습니다(2-4). |
| 허용되지 않은 요청, CSRF 검증 실패 | HTTP 403과 "접근할 수 없습니다" 화면. CSRF 실패는 경로와 관계없이 403입니다(2-4). |
| 그 밖의 요청 오류(400, 405 등) | 같은 상태 코드와 "요청을 처리할 수 없습니다" 화면(2-5). |
| 서버 오류(5xx) | 같은 상태 코드와 "일시적인 오류가 발생했습니다" 화면. 예외 이름, 스택 트레이스, DB 정보는 표시하지 않습니다(2-5). |
| 가격 정보가 누락된 상품 | 해당 상품 가격이 없는 판매점은 완전 비교 목록에서 제외하고 부분 비교 목록에 표시합니다. 0원으로 계산하지 않고, 품절로 표현하지 않습니다. |
| 기준 조사일 가격이 어느 판매점에도 없는 상품을 담고 비교 | 검색과 담기는 허용합니다. 비교에서는 가격 누락 정책(R4, R5)을 그대로 적용합니다. 이 상품이 모든 판매점에서 누락되므로 완전 비교 판매점이 없고, 다른 상품 가격이 있는 판매점은 부분 비교 목록에 이 상품을 "가격 정보 없음"으로 표시합니다. 담은 상품 모두 가격이 없으면 "가격이 확인된 판매점 없음"을 안내합니다. |
| 상품 검색에서 잘못된 페이지 번호 | 음수·0·숫자가 아닌 값은 첫 페이지로, 전체 페이지 수를 넘는 값은 마지막 페이지로 보정합니다. 검색 결과 0건은 정상 처리합니다. |
| 선택 지역에 비교 대상 판매점이 없음 | 비교할 판매점이 없다는 사유를 안내합니다. |
| 선택 지역에 판매점은 있으나 완전 비교 가능한 판매점이 없음 | 완전 비교 가능한 판매점이 없다는 사유를 안내합니다(판매점 없음과 구분). 부분 비교 목록에 확인된 상품별 가격, 누락 상품, 확인된 상품의 합계(`knownSubtotal`)를 표시합니다. |
| 총액이 같은 판매점 | 판매점 ID 숫자 오름차순으로 일정하게 정렬하고, 순위 숫자는 표시하지 않습니다(R6). |
| `담기`로 수량이 99를 넘는 경우 | 추가를 거부하고 수량 제한을 안내합니다. 99로 조용히 조정하지 않습니다. |
| 장바구니에서 잘못된 수량 입력(0, 음수, 100 이상, 정수가 아닌 값) | 요청을 거부하고 오류 메시지를 표시합니다. 화면과 서버 양쪽에서 검증합니다. |
| 로그인 실패 | 아이디가 없는 경우와 비밀번호가 틀린 경우를 구분하지 않는 동일한 메시지를 표시합니다. |
| 비회원과 회원의 장바구니 저장 방식 차이 | 비회원은 세션(세션 종료 시 소멸), 회원은 DB(재로그인 후 유지). 로그인 시 병합하지 않습니다. |
| 다른 회원의 장바구니 접근 시도 | 서버가 인증된 회원 ID로만 장바구니를 조회·수정하므로 접근할 수 없습니다. 비회원 요청도 DB 장바구니에 접근할 수 없습니다. |
| 수집 중 API 호출 실패 | 정상적인 빈 응답과 구분하며, "가격 데이터 없음"으로 저장·표시하지 않습니다. 민감정보 없이 원인을 기록합니다(4-3). |

- 회원 장바구니 저장, 다른 회원 장바구니 접근 항목은 Phase 5에서 구현했습니다. 회원가입은 5-1, 로그인 실패 처리는 5-2, 회원 장바구니 서비스는 5-3, 화면 연결과 접근 제한 흐름 테스트는 5-4에서 구현했습니다.
